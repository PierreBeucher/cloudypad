# Cloudy Pad release plan

Consolidated needs for the Cloudy Pad release process. This plan replaces the
current `release-please`-based process (`hack/release-create.sh`) with a simpler,
self-contained, idempotent release script. Release notes are generated with
[git-cliff](https://git-cliff.org).

## Why replacing the current process

Current process (`hack/release-create.sh` + `release-please`) has these flaws:

- CI success is never checked: the script polls `status == "completed"`, not
  `conclusion == "success"`. A failed Docker build can still be merged to master
  and published as "latest".
- Version mismatch trap: the script takes a user-entered version, but
  release-please computes its own version from conventional commits. If they
  differ, the release PR, tag, and stamped files disagree.
- The "Continue?" prompt discards the answer (any input continues).
- No preflight checks: clean tree, base branch, token, semver validity.
- Not idempotent: failure mid-way leaves pushed branches, merged PRs, tags,
  prereleases, images. Re-running fails on existing branch.
- `gh release list -L 1` races: prerelease/latest flags operate on "the first
  release in the list", not necessarily the one just created.
- Silent `sed` no-ops: version substitutions never verify they matched.
- Unpinned `npx --yes release-please`; token passed on argv.
- Extra complexity: release-please PR + prerelease→latest dance for a
  mechanical version stamp.

## Process overview

- All release work happens on branch `release-$V`: version stamp, changelog,
  tag, CI watch, image verification, GitHub release.
- The script **never commits or pushes to master**.
- The script ends by opening a PR `release-$V` → `master`. It **does not merge
  it**. Merging the PR is the final, human action.

## Key constraint: merging the PR is the go-live point

Users install via `master/install.sh`, which pins `v$V`; `cloudypad.sh` then
pulls `ghcr.io/pierrebeucher/cloudypad:$V`. As soon as master contains the
version stamp, the release is live for every new install.

Consequences:

- The PR is only opened after Release CI succeeded and images are verified:
  merging it is always safe.
- Between GitHub release publication and PR merge, GitHub shows `v$V` as
  latest while master install still serves the previous version. Harmless:
  tag and images for `v$V` exist.
- PR must be merged with a **merge commit** (not squash, not rebase): tag
  `v$V` must stay reachable from master, otherwise next git-cliff run cannot
  find the release boundary and re-lists commits. Stated in the PR body.

## Artifacts produced by a release

All on branch `release-$V`:

- Version stamp in: `package.json`, `cloudypad.sh` (`CLOUDYPAD_VERSION`),
  `install.sh` (`DEFAULT_CLOUDYPAD_SCRIPT_REF=v$V`), `flake.nix`
  (`cloudypadVersion` + recomputed `cloudypad.sh` sha256 hash)
- `CHANGELOG.md` section for `$V`
- Annotated Git tag `v$V` on the stamp commit
- Docker images pushed to ghcr.io, tagged `$V` (by the tag-triggered Release
  workflow):
  - `ghcr.io/pierrebeucher/cloudypad` (core, multi-arch linux/amd64+linux/arm64)
  - `ghcr.io/pierrebeucher/cloudypad/sunshine`
- GitHub release on tag `v$V`, marked latest, body = `CHANGELOG.md` section
- PR `release-$V` → `master`, left open

Note: the CLI version displayed by the binary comes from `package.json`
(`src/core/const.ts` imports it) — no other version constant to stamp.

## Release notes generation

Tool: `git-cliff`, configured by `cliff.toml` at repo root, added to the flake
dev shell.

- Range: commits since previous `v*` tag (`--unreleased`)
- Kept: `feat`, `fix`, `perf` (grouped as Features / Bug Fixes / Performance),
  breaking changes flagged
- Skipped: other conventional types (`chore`, `dev`, `docs`, `test`,
  `refactor`, ...), non-conventional commits (`sunshine:`, `wip:`, merges...),
  and the stamp commit `chore(release): v$V`
- Output format matches the existing `CHANGELOG.md` entries (version compare
  link, date, scope in bold, short SHA commit link)
- Duplicates are not deduplicated: output is used as-is
- Next version: `git cliff --bumped-version` (configured for 0.x:
  `feat` bumps minor, breaking does not bump major)

Generated section is inserted below the `# Changelog` title of `CHANGELOG.md`
and used as-is, no manual review step.
The GitHub release body is **extracted from the committed `CHANGELOG.md`**
(section `## [$V]` up to next `## [`), never from a temp file: resume does not
depend on local leftovers.

Existing `CHANGELOG.md` history is kept as-is (no regeneration).

## Script usage

Plain Bash script (`set -euo pipefail`), one function per step, each step
split into a `*_done` check and a `*_do` action. Fully automated: no prompt,
no confirmation. Any unexpected condition fails with a non-zero exit and an
explicit message; re-running resumes.

```sh
novops load -e release   # GITHUB_TOKEN
task release-create -- [VERSION]
```

Version resolution (`$V`, plain `X.Y.Z`):

1. `VERSION` argument if given
2. Otherwise, an open `release-*` PR or remote `release-*` branch exists:
   reuse its version (resume). More than one: fail, ask for explicit `VERSION`.
3. Otherwise, `git cliff --bumped-version` (printed, used as-is)
4. Explicit `VERSION` given while another release is in progress: fail

Options:

- `CLOUDYPAD_RELEASE_DRY_RUN=true` — run Step 1 locally (stamp + commit on local
  `release-$V`), print diff and notes, push nothing, stop.
- `--abort` — undo an unmerged release (see [Abort](#abort)).

## Idempotency model

The script is safe to re-run at any point with the same version: it derives
the current progress from remote state (not local files) and skips completed
steps. Each step is `check done → skip` or `do → verify`.

Derived names: branch `release-$V`, tag `v$V`.

Progress detection, evaluated in this order (after `git fetch --tags origin`):

| Condition                                                   | Meaning                         | Resume at       |
| ----------------------------------------------------------- | ------------------------------- | --------------- |
| PR `release-$V` → `master` merged                           | Released and live               | Nothing, exit 0 |
| GitHub release `v$V` published (latest, non-draft)          | Published, PR missing or open   | Step 6          |
| Remote tag `v$V` exists                                     | Tagged, CI pending/failed/done  | Step 3          |
| `origin/release-$V` HEAD is a valid stamp commit            | Stamped, not tagged             | Step 2          |
| `origin/release-$V` exists without stamp commit             | Branch prepared, not stamped    | Step 1 (reuse)  |
| None of the above                                           | Fresh release                   | Step 0          |

"Valid stamp commit" = subject is `chore(release): v$V` and the consistency
check (Step 1) passes on it.

Inconsistent states fail loudly, never auto-fixed:

- Remote tag `v$V` exists but does not point to the stamp commit on
  `origin/release-$V` (or the branch is gone)
- `origin/release-$V` has commits on top of the stamp commit
- PR `release-$V` closed without merge

## Steps

### Step 0 — Preflight (fail fast, before touching anything)

Always:

- Tools present: `git`, `gh`, `jq`, `git-cliff`, `nix-prefetch-url`, `docker`
- `GITHUB_TOKEN` set; `gh auth status` OK
- `$V` matches `^[0-9]+\.[0-9]+\.[0-9]+$` (no `v` prefix, no prerelease or
  build suffix: prereleases are not supported)
- Working tree clean

Fresh release only:

- `origin/master` fetched; release branch will start from it (current local
  branch does not matter)
- `$V` greater than latest `v*` tag (`sort -V`)
- Previous release tag is reachable from `origin/master` (previous release PR
  merged with a merge commit), otherwise git-cliff range is wrong
- No open `release-*` PR for another version
- `git cliff --unreleased` yields at least one entry, otherwise fail: nothing
  user-facing to release

### Step 1 — Create or reuse branch, stamp (single commit)

- `origin/release-$V` exists: check it out (reuse). Otherwise create
  `release-$V` from `origin/master`. A leftover local branch without remote
  counterpart (eg. from a dry run) is discarded.
- Generate the `$V` section with git-cliff, insert below `# Changelog` as-is
  (skip insertion if `## [$V]` already present)
- Stamp versions in `package.json`, `cloudypad.sh`, `install.sh`, `flake.nix`
- Compute `flake.nix` hash **after** stamping `cloudypad.sh`:
  `nix-prefetch-url file://$PWD/cloudypad.sh --type sha256`
- Consistency check, fail if any mismatch:
  - `package.json` == `CLOUDYPAD_VERSION` == `install.sh` ref == `flake.nix`
    version == `$V`
  - `flake.nix` hash == hash of committed `cloudypad.sh`
  - `CHANGELOG.md` contains `## [$V]`
  - each substitution matched exactly once (no silent `sed` no-op)
- Commit `chore(release): v$V` on `release-$V`
- Dry run: stop here
- Push `release-$V` (no workflow triggers on non-master branch pushes)

### Step 2 — Tag

- Create annotated tag `v$V` on `origin/release-$V` HEAD (stamp commit), push
  tag
- Leftover local tag `v$V` without remote counterpart (interrupted run): push
  it if it points to the stamp commit, otherwise delete and recreate it
- Tag push triggers the `Release` workflow (core + sunshine images)

### Step 3 — Watch CI

- Find the `Release` run for the tag commit, most recent one (a rerun keeps
  the same run ID with a new attempt):
  `gh run list --workflow release.yml --event push --commit <sha> --json databaseId,status,conclusion,url`
- Run not listed yet: poll a few minutes (GitHub may take time to register it)
- `in_progress`/`queued`: `timeout 3600 gh run watch <id> --exit-status`
  (`gh run watch` has no timeout of its own; timeout = exit non-zero,
  re-running the script resumes watching)
- Require **`conclusion == "success"`**
- On failure: print run URL and the rerun command
  (`gh run rerun <id> --failed`), exit non-zero. After rerunning, re-running
  the script resumes here. For a code problem, use `--abort`.

### Step 4 — Verify images and flake hash

Read-only, always runs:

- `docker manifest inspect` both image tags `$V`
- Core image manifest lists `linux/amd64` and `linux/arm64`
- Flake hash matches the file actually served for the tag:
  `curl -fsSL https://raw.githubusercontent.com/PierreBeucher/cloudypad/v$V/cloudypad.sh`
  then `nix hash file --type sha256 --base32` == `flake.nix` hash at tag `v$V`.
  Do not rely on `nix build .#` alone: Step 1 `nix-prefetch-url file://...`
  already added a store path with that hash, so the fixed-output fetch would be
  satisfied locally without downloading from GitHub.
- Published core image runs and reports the expected version, fail otherwise:
  `docker run --rm ghcr.io/pierrebeucher/cloudypad:$V --version` == `$V`
  (host architecture only; sunshine image covered by manifest check only)
- Optional: `test-install.sh` against the tag

### Step 5 — Publish GitHub release

- Release body extracted from `CHANGELOG.md` at tag `v$V`
- Release absent: `gh release create v$V --verify-tag --latest --title v$V --notes-file <file>`
- Release present: `gh release edit v$V --latest --draft=false --prerelease=false`
  (converges to expected state)

### Step 6 — Open PR to master (not merged)

- PR `release-$V` → `master` absent: `gh pr create --base master --head release-$V --title "Release v$V" --body <...>`
- PR present and open: no-op, print URL
- PR body: release notes + link to GitHub release and Release run + explicit
  "merge with merge commit, do not squash/rebase"
- Script ends by printing the PR URL. Human reviews and merges.

Branch `release-$V` is not deleted by the script: it is the PR head. Rely on
GitHub "automatically delete head branches" after merge, or delete manually.

## Abort

`--abort` undoes a release whose PR is **not merged**. If the PR is merged,
refuse: fix forward with a new patch release.

- Close PR `release-$V` if open
- Delete GitHub release `v$V` if any
- Delete remote and local tag `v$V`
- Delete remote and local `release-$V`

Images `$V` possibly pushed to ghcr.io are left as-is: unreferenced, they are
overwritten if `$V` is released again. Hence no "image tag exists" preflight
check: release completion is defined by GitHub release + merged PR only.

## Invariants

- The script never writes to master. Master only changes when a human merges
  the release PR.
- The PR is only opened once Release CI succeeded, images are verified and
  GitHub release is published.
- `install.sh` and `flake.nix` on master fetch from `v$V`: the tag exists
  before the stamp can reach master.
- `flake.nix` sha256 is computed from the exact `cloudypad.sh` bytes committed
  in the stamp commit. One commit suffices.
- Tag `v$V` always points to the stamp commit and is reachable from master
  after PR merge (merge commit only).
- Docker image tags derive from the Git tag (`${GITHUB_REF_NAME#v}`): tag name
  and image tag must agree.
- Image cache tags (`-cache`, `master-cache`) used by release builds are
  maintained by the test-unit workflow — unaffected by this migration.

## Requirements to run a release

- `GITHUB_TOKEN` with repo contents write + pull requests write (novops
  release environment)
- Git push credentials for `origin` (release branch and tag only)
- `gh`, `jq`, `git-cliff`, `nix-prefetch-url`, docker (nix dev shell)
- Self-hosted runner with Docker buildx for the Release workflow (existing)

## CI on the release PR

The release PR (head ref `release-*`) runs no CI job. Tests already ran on
master before the release, release images are built and verified by the
tag-triggered `Release` workflow and Step 4, and the release commit only
stamps versions and changelog.

- `test-unit.yml`: skip all jobs with
  `if: "!startsWith(github.head_ref, 'release-')"`
- `test-integ.yml`: skip `integ-test` with the same condition
- Existing `release/` prefix in `test-unit.yml` conditions is wrong (branches
  are `release-*`, the skip never applied): replaced by the condition above
